# Qualification reference

[Back to the README](../README.md) · [Repository setup](integration.md) · [Local reproduction](development.md)

The following details describe host preparation, platform gates, retained evidence and rollout diagnostics.

## Qualification

By default, every individual package PR, fleet run, canary and npm release qualifies the **latest stable official Pi** and the **latest maintained `fitchmultz/pi` main**. This automation repository [selects fleet runs by change scope](development.md#ci-scope); an intentional docs/policy/validator-only skip is not fleet qualification. Runtime/reusable-workflow changes and manual dispatches still require the full fleet. An explicit immutable `fork-ref` qualifies that candidate instead. There is no hard-coded host-version inventory or old-baseline comparison. The canonical `resolve-hosts.yml`/`resolveHostTargets` resolver resolves current identities once per run, then all jobs reuse the exact official version and fork SHA. A newly published host cannot silently change a later job's graph. The resolver verifies publication of the whole official Pi workspace cohort before scheduling checks; partial publication fails closed rather than falling back to an older release.

The reusable workflow's `host` input accepts only `both` (default) or `fork`; other values fail resolution. Normal extension PRs and the fleet canary leave it at `both`, preserving latest official/fork qualification for all applicable packages across all 24 repositories. A fork reverse-dependency caller uses `host: fork` with `repository: all`. That mode qualifies the same 24 Pi-host-qualified fleet packages against the exact `fork-ref` and retains every configured Node/platform lane. Fork-only selection does not read candidate manifests for host selection or query/preflight official npm metadata (even if `official-version` is supplied). The former standalone CLI (`pi-evidence`) and extensions `pi-local-agents-only` and [`pi-edit-session-in-place`](https://github.com/fitchmultz/pi-edit-session-in-place) are retired from qualification, canary and npm-release planning. Their archived GitHub repositories retain their history; existing npm versions remain published. Unrelated official-host failures therefore do not block fork changes.

CI installs the reviewed npm version from `package.json#packageManager` on every Node baseline; routine updates to that metadata are reviewed manually. Each host gets its own source-bound production graph through native `npm ci --ignore-scripts --omit=dev --include=optional`. Official preparation verifies the exact release's GitHub installer manifest/lock against GitHub asset digests, vendor `SHA256SUMS` and the immutable release tag's source files. It verifies the complete Pi cohort's registry declarations and fills only its prepublication lock entries' missing published integrities; third-party resolutions, the vendor's overrides and optional platform dependencies remain unchanged. Missing or mismatched publication fails closed, with no older-release fallback or fork-lock substitution.

The fork uses `produceArtifactSet` from that exact fork commit's `scripts/package-artifacts.mjs` with `build: false`, preserving built source and frozen model data. Packing verifies the production installer inputs against that commit, retains their exact bytes and full digests, and uses the fork's maintained `wireConsumer` helper to substitute only its local Pi archives into the consumer manifest/lock. Every fork job consumes that same frozen artifact. Host receipts identify both original and applied locks, native artifact identities/integrities, SDK/CLI hashes, the installed runtime tree digest and physical package paths.

Development selection uses npm-managed external `file:` directory links (`--install-links=false`) to the prepared Pi cohort and its actual TypeBox package. npm does not install those external packages' dependencies again; their real paths, complete installed runtime tree and lock digests must remain identical. Native `npm ci --dry-run --ignore-scripts` retains the original source-lock consistency gate without first installing the old host. The extension's own development dependencies still use its native npm lock. Its public source manifest and lockfile are restored byte-for-byte, even on selection failure, before package checks and packing. These managed-host proofs do **not** certify ordinary unlocked npm publication: independent Git/npm production consumer installs retain their normal dependencies, lifecycle and real failures.

For applicable fork lanes, the resolver queries `fitchmultz/pi`'s maintained `main` once per run and validates its full commit SHA. An explicit full-SHA `fork-ref` bypasses that lookup; invalid refs or failed resolution stop qualification. Host-free CLI runs do not resolve the fork. The resolved SHA is reused for checkout, build, cache identity, artifacts and qualification receipts; it never floats within a run. Third-party actions and reusable automation remain pinned to reviewed commits.

The fork is built once per workflow and shared as an artifact. Its cache includes runner architecture, Node version, fork commit, automation revision, lockfile and hydrated model-data contents. An integrated fork reverse-dependency caller supplies `fork-ref: ${{ github.sha }}` and its existing `fork-source-artifact` from the same run, so all gates use that exact commit and frozen model data. It preserves `source-ref: ${{ vars.PI_COMPATIBILITY_SOURCE_REF || 'main' }}` for candidate rollout branches, then default-branch qualification. Other public callers build directly from public source without cross-repository artifact credentials.

Required lanes run the repository's contracts, a fresh Git checkout with production dependencies and normal install lifecycle, and the real bundled Pi CLI. Owned npm channels also pack and install a real tarball, then compare its registered tools, active tools, commands and provider surface with the Git consumer. The CLI observer also loads each consumer's shipped themes through the selected host's public `DefaultResourceLoader`, preserving native package discovery and exclusions and failing on theme diagnostics. RPC UI and editor rendering are not exercised by that check; package-owned native UI contracts cover those surfaces. Skills and the standalone CLI retain their resource/CLI contracts instead of being treated as fictitious extensions. Workflows qualifies as an extension with public packaged resources and real profile composition, preserving its project Git use. Package identities in `fleet.json` are explicit: a matching npm name alone is not ownership evidence.

Package contract commands have a 10-minute watchdog by default. Posthorse's Linux and macOS commands have a 20-minute budget for pinned native checker compilation: the cold Rust and Go builds alone took 5m14s and 5m19s on the hosted Linux runner, before its contract tests. Apply Edits retains 20 minutes on Linux and uses 30 minutes (1800000ms) on macOS for the whole contract command, including cold Rust/Go preparation, policy/lint/format/typecheck, the full test suite and pack check. Posthorse, Apply Edits, Subagents and Browser lanes install Go 1.27.1 without a toolchain cache. Only Posthorse and Apply Edits install Rust 1.99.0 with llvm-tools, without a toolchain cache; they put the physical Rust toolchain's bin directory on PATH so compilation remains available under qualification's isolated HOME rather than relying on rustup's home configuration. The fleet inventory gives Browser's Linux and macOS contract commands 30 minutes, matching its maintained full-CI envelope for cold Go quality-checker preparation, the full serial suite and package smoke; its Windows contract command retains 45 minutes. Both latest-host Linux lanes hit the former 15-minute outer command watchdog with partial TAP output and no final counts; that evidence does not identify an inner build or assertion hang or prove the new budget sufficient. Browser's non-Windows qualification jobs allow 45 minutes: 30 for contracts plus 15 for host/development preparation and consumer checks. Apply Edits' macOS job also allows 45 minutes: 30 for the whole contract command plus 15 for setup, host/development preparation, consumer checks and finalization. Browser's Windows job retains a 70-minute limit and Cursor's Windows job 35 minutes for cold installation and the remaining consumer checks; Subagents jobs have the composed budget below; other jobs retain 25 minutes. The Windows qualification step uses native timeouts of 60 minutes for Browser, 25 for Cursor and 15 for other packages, leaving 10 minutes within the unchanged job ceilings for setup, cancellation settlement (up to five minutes) and artifact upload. A step-only timeout is a failed diagnostic covered by the Windows waiver; job/global cancellation still fails closed. Non-Windows steps retain GitHub's default 360-minute ceiling, so their existing job and contract limits remain controlling. Before qualification, CI writes actual lane inputs to `lane-inputs.txt` and streams emitted stdout/stderr to `qualification.log` without hiding command failure. The existing always-run upload can retain these partial files after an ordinary step timeout; they are not completed qualification or host provenance, and a hard kill can prevent finalization, reports, probes or artifact upload. These are whole-command, whole-step and whole-job CI budgets; individual tests and production deadlines remain unchanged. Each qualification receipt records the selected command budget.

Apply Edits' required official/macOS lane in source CI `38007300942` exhausted the former 20-minute command budget after a 589-pass prefix, without final counts or an assertion failure. A completed same-source/official-host control took 12m26s, with 685 tests, 680 passes, five platform skips, no failures/cancellations, pack check and fresh Git/CLI consumer proof. Cold Rust compilation took 9m29s in the failed lane versus 5m39s in that control; 190 shared quality probes were median 1.644× slower. This strongly supports cumulative cold/slow-runner budget pressure, but does not prove the historical interleaving or exclude a late hang, and the new allowance does not guarantee qualification. Contract stdout/stderr remain buffered and are published after the command; the existing CI `tee` captures emitted parent output without sharing its endpoint with contract descendants.

Subagents' Linux and macOS contract commands have a 59-minute budget (3540000ms). The explicit sequential recipe allows 41 minutes for CI (quality/native preparation 15 + build/package 5 + install smokes 5 + integration 15 + settlement 1), then 17 minutes for editor preparation/metadata and native package smoke (5 + 5 + 1 + 5 + 1), plus one minute for outer settlement. Its reusable qualification job allows 120 minutes: contract/settlement 59 + host/development preparation 30 + production installs/smokes 15 + fork/tooling 15 + final settlement 1. These limits enclose the composed recipe; they do not certify an unmerged process-lifecycle implementation or replace current required qualification. Subagents' unit 300000ms, integration 900000ms, native 110-second controls and production/assertion deadlines remain unchanged.

Linux qualification uses private `/var/tmp/pc-*` roots to avoid the Ubuntu 26 `/tmp` quota that stopped native Go compilation before tests; macOS keeps short `/tmp` roots for Unix sockets, and Windows keeps its native temporary directory. Each qualification owns `GOMODCACHE` under its root. Finalization attempts probe publication, then uses `go clean -modcache` to remove Go's read-only extracted modules before deleting that root. Copy and cleanup failures fail qualification while preserving the original primary error and recording any secondary errors in operation order. `qualification.json` is written after finalization, so cleanup failure cannot leave a passing report. Ambient Go caches are neither reused nor cleaned.

Posthorse qualifies its native compaction-based rollover, recovery history and retain-none behavior on both current hosts; it does not require retired fork checkpoint APIs. The kit's Unix terminal contract exercises the current fork's managed launcher restart; its legacy multi-session helper is not activated inside that launcher.

**Windows qualification is owner-waived for this rollout (September 21, 2026).** Windows matrix jobs remain visible diagnostics and retain their actual failures and artifacts, but they do not gate merges or releases. Because the required check still waited for them, `Automation CI` omits Windows matrix lanes on PRs and pushes; the daily canary, manual `Automation CI` dispatches and individual package callers still run them. The Windows environment self-check is also non-blocking. This waiver is not a Windows pass or a claim that the known Browser process-coordination failures are fixed. Linux/macOS, Node floors, host identity, consumer artifacts and the three owner-designated final reviews remain required. Restore the Windows gate through a reviewed follow-up after the recorded failures are resolved.

Historical support floors and locked development dependencies do not select validation hosts. Node/OS lanes are selected by the fleet and existing repository-specific workflows. Additional platform lanes use the latest Node 24 release; the primary platform also tests the declared Node floor. Native `setup-node` version resolution checks for the latest release matching each selector rather than accepting an older runner-cache entry; exact floor selectors remain exact. Routine checks use empty profiles and no provider credentials. These results do not certify live browser, Cursor, Oracle, OAuth or desktop operations. Those existing release gates remain separate when a shipped change touches their behavior. An unavailable platform must be recorded as unqualified or explicitly waived, never counted as passed.

Windows jobs initialize `PSModulePath` through the runner's native PowerShell shell (`pwsh`) and carry its value into bash using GitHub's environment file. Isolation retains that native module path alongside Windows runtime variables; HOME, configuration and temp roots remain private, without inherited credentials. The diagnostic `windows-environment` self-check uses the same setup and runs a real `Get-Process` identity query under that isolation via bash. It warms ambient PowerShell once to separate cold CLR startup from the environment regression, then enforces the consumer's 5-second query bound. The `automation` aggregate excludes this owner-waived native diagnostic; its outcome is never presented as required Windows qualification.

## Results and the maintenance loop

`compatibility` is the stable aggregate job. It requires resolution, the fork artifact when applicable, and every required matrix lane. Cancellation, missing jobs and required-lane failures do not become successful qualification. GitHub checks and job summaries show the result; `qualification-*` artifacts contain per-lane provenance, failures, consumer CLI output and tested npm tarballs.

The scheduled `Pi release canary` checks all default branches against the latest stable release and the maintained fork, including the existing owned npm releases. It uses Actions concurrency and keeps exactly one native GitHub issue per affected repository, covering both official and fork hosts. Each run updates that issue with the latest lanes and closes it once every required lane for the repository passed with complete evidence; owner-waived Windows lanes are listed as diagnostics but do not keep an issue open. Older per-host/per-version issues for the same repository are folded into the single issue and closed. A failed runner without package evidence gets an infrastructure issue, closed by the next successful fleet run. The canary creates no repair PR, publishes nothing, and never updates a user's Pi installation.

Repairs use the repository's ordinary PR process. A fixture or host-selection failure is repaired there; a product failure gets a focused regression and source fix. The automation's own native tests deliberately introduce factory/startup failures and require the real bundled CLI to reject them, proving that the gate cannot pass solely because a process started. Metadata tests cover incomplete publication and exact cohort selection; resolver-entrypoint tests cover default and fork-only lanes, source refs and fail-closed selection with mocked external fetches; report tests cover one issue per repository across hosts, legacy-issue consolidation, owner-waived diagnostics and complete-evidence closure.
