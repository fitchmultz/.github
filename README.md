# Pi release compatibility

Shared Renovate policy and native GitHub Actions qualification for the Pi packages in `fleet.json`. Official stable releases are the primary host. The maintained `fitchmultz/pi` fork is a separate required host.

## Repository callers

Each repository owns its source, lockfile, package-specific `check:compat` command, and release channel. Its small workflow calls `.github/workflows/pi-compatibility.yml` at a reviewed commit and passes that same commit as `automation-ref`. Keep both pins together. The shared Renovate preset groups those references and groups declared Pi development dependencies into one stable-version update PR. It preserves declared dependency ranges; development lockfiles are reproducible snapshots, not qualification targets. It leaves wildcard host peers alone and does not enable automerge.

For reviewed automation revisions on `main` without a release tag, annotate both immutable SHA pins with `# main`. Renovate tracks that branch's digest for both references in the same update group; the workflow still executes the reviewed SHA, never a floating automation branch.

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["github>fitchmultz/.github:pi-extensions"]
}
```

The managed Renovate GitHub App must have access to the selected repositories. A checked-in config does not install the App. Host qualification resolves current releases automatically; the fork's own npm dependencies continue to follow its reviewed upstream-integration process.

## Qualification

Every individual PR, fleet run, canary and npm release qualifies the **latest stable official Pi** and the **latest maintained `fitchmultz/pi` main**. There is no hard-coded host-version inventory or old-baseline comparison. The canonical `resolve-hosts.yml`/`resolveHostTargets` resolver resolves current identities once per run, then all jobs reuse the exact official version and fork SHA. A newly published host cannot silently change a later job's graph. The resolver verifies publication of the whole official Pi workspace cohort before scheduling checks; partial publication fails closed rather than falling back to an older release.

The reusable workflow's `host` input accepts only `both` (default) or `fork`; other values fail resolution. Normal extension PRs and the fleet canary leave it at `both`, preserving latest official/fork qualification for all applicable packages across all 26 repositories. Only the fork's reverse-dependency CI passes `host: fork` with `repository: all`. That mode qualifies the same 26 Pi-host-qualified fleet packages against the exact `fork-ref` and retains every configured Node/platform lane. The former standalone CLI (`pi-evidence`) is archived and no longer in the fleet. It does not read candidate manifests for host selection or query/preflight official npm metadata (even if `official-version` is supplied). Unrelated official-host failures therefore do not block fork changes.

CI installs the reviewed npm version from `package.json#packageManager` on every Node baseline; Renovate maintains that standard metadata. Each host gets an independent npm dependency graph. The latest official cohort is frozen to its resolved version for that run; the fork uses `produceArtifactSet` from that exact fork commit's `scripts/package-artifacts.mjs` with `build: false`, preserving the already-built source and frozen model data. Host preparation records the SDK and bundled CLI hashes, cohort, lock integrity or fork tarball hashes, Node version, and resolved paths. The selected host's TypeBox version is used rather than assumed to follow Pi's version number. The public source manifest and lockfile are restored before package checks; the selected installed graph remains in place for types and imports.

For applicable fork lanes, the resolver queries `fitchmultz/pi`'s maintained `main` once per run and validates its full commit SHA. An explicit full-SHA `fork-ref` bypasses that lookup; invalid refs or failed resolution stop qualification. Host-free CLI runs do not resolve the fork. The resolved SHA is reused for checkout, build, cache identity, artifacts and qualification receipts; it never floats within a run. Third-party actions and reusable automation remain pinned to reviewed commits.

The fork is built once per workflow and shared as an artifact. Its cache includes runner architecture, Node version, fork commit, automation revision, lockfile and hydrated model-data contents. The fork's reverse-dependency caller supplies `fork-ref: ${{ github.sha }}` and its existing `fork-source-artifact` from the same run, so all gates use that exact commit and frozen model data. It preserves `source-ref: ${{ vars.PI_COMPATIBILITY_SOURCE_REF || 'main' }}` for candidate rollout branches, then default-branch qualification. Other public callers build directly from public source without cross-repository artifact credentials.

Required lanes run the repository's contracts, a fresh Git checkout with production dependencies and normal install lifecycle, and the real bundled Pi CLI. Owned npm channels also pack and install a real tarball, then compare its registered tools, active tools, commands and provider surface with the Git consumer. Skills and the standalone CLI retain their resource/CLI contracts instead of being treated as fictitious extensions. Workflows qualifies as an extension with public packaged resources and real profile composition, preserving its project Git use. Package identities in `fleet.json` are explicit: a matching npm name alone is not ownership evidence.

Package contract commands have a 10-minute watchdog by default. Posthorse's Linux and macOS commands have a 20-minute budget for pinned native checker compilation: the cold Rust and Go builds alone took 5m14s and 5m19s on the hosted Linux runner, before its contract tests. Apply Edits uses a 20-minute command budget on Linux and macOS for the same cold native checker preparation; its hosted Linux run completed Rust compilation, Go preparation, lint, formatting and typecheck before the former 10-minute watchdog interrupted the test phase. Posthorse, Apply Edits, Subagents and Browser lanes install Go 1.27.1 without a toolchain cache. Only Posthorse and Apply Edits install Rust 1.99.0 with llvm-tools, without a toolchain cache; they put the physical Rust toolchain's bin directory on PATH so compilation remains available under qualification's isolated HOME rather than relying on rustup's home configuration. The fleet inventory gives Browser's Linux and macOS contract commands 30 minutes, matching its maintained full-CI envelope for cold Go quality-checker preparation, the full serial suite and package smoke; its Windows contract command retains 45 minutes. Both latest-host Linux lanes hit the former 15-minute outer command watchdog with partial TAP output and no final counts; that evidence does not identify an inner build or assertion hang or prove the new budget sufficient. Browser's non-Windows qualification jobs allow 45 minutes: 30 for contracts plus 15 for host/development preparation and consumer checks. Browser's Windows job retains a 70-minute limit and Cursor's Windows job 35 minutes for cold installation and the remaining consumer checks; Subagents jobs have the composed budget below; other jobs retain 25 minutes. These are whole-command and whole-job CI budgets; individual tests and production deadlines remain unchanged. Each qualification receipt records the selected command budget.

Subagents' Linux and macOS contract commands have a 59-minute budget (3540000ms). The explicit sequential recipe allows 41 minutes for CI (quality/native preparation 15 + build/package 5 + install smokes 5 + integration 15 + settlement 1), then 17 minutes for editor preparation/metadata and native package smoke (5 + 5 + 1 + 5 + 1), plus one minute for outer settlement. Its reusable qualification job allows 120 minutes: contract/settlement 59 + host/development preparation 30 + production installs/smokes 15 + fork/tooling 15 + final settlement 1. These limits enclose the composed recipe; they do not certify an unmerged process-lifecycle implementation or replace current required qualification. Subagents' unit 300000ms, integration 900000ms, native 110-second controls and production/assertion deadlines remain unchanged.

Linux qualification uses private `/var/tmp/pc-*` roots to avoid the Ubuntu 26 `/tmp` quota that stopped native Go compilation before tests; macOS keeps short `/tmp` roots for Unix sockets, and Windows keeps its native temporary directory. Each qualification owns `GOMODCACHE` under its root. Finalization attempts probe publication, then uses `go clean -modcache` to remove Go's read-only extracted modules before deleting that root. Copy and cleanup failures fail qualification while preserving the original primary error and recording any secondary errors in operation order. `qualification.json` is written after finalization, so cleanup failure cannot leave a passing report. Ambient Go caches are neither reused nor cleaned.

Posthorse qualifies its native compaction-based rollover, recovery history and retain-none behavior on both current hosts; it does not require retired fork checkpoint APIs. The kit's Unix terminal contract exercises the current fork's managed launcher restart; its legacy multi-session helper is not activated inside that launcher.

**Windows qualification is owner-waived for this rollout (September 21, 2026).** Windows matrix jobs remain visible diagnostics and retain their actual failures and artifacts, but they do not gate merges or releases. The Windows environment self-check is also non-blocking. This waiver is not a Windows pass or a claim that the known Browser process-coordination failures are fixed. Linux/macOS, Node floors, host identity, consumer artifacts and the three owner-designated final reviews remain required. Restore the Windows gate through a reviewed follow-up after the recorded failures are resolved.

Historical support floors and locked development dependencies do not select validation hosts. Node/OS lanes are selected by the fleet and existing repository-specific workflows. Additional platform lanes use the latest Node 24 release; the primary platform also tests the declared Node floor. Native `setup-node` version resolution checks for the latest release matching each selector rather than accepting an older runner-cache entry; exact floor selectors remain exact. Routine checks use empty profiles and no provider credentials. These results do not certify live browser, Cursor, Oracle, OAuth or desktop operations. Those existing release gates remain separate when a shipped change touches their behavior. An unavailable platform must be recorded as unqualified or explicitly waived, never counted as passed.

Windows jobs initialize `PSModulePath` through the runner's native PowerShell shell (`pwsh`) and carry its value into bash using GitHub's environment file. Isolation retains that native module path alongside Windows runtime variables; HOME, configuration and temp roots remain private, without inherited credentials. The diagnostic `windows-environment` self-check uses the same setup and runs a real `Get-Process` identity query under that isolation via bash. It warms ambient PowerShell once to separate cold CLR startup from the environment regression, then enforces the consumer's 5-second query bound. The `automation` aggregate excludes this owner-waived native diagnostic; its outcome is never presented as required Windows qualification.

## Results and the maintenance loop

`compatibility` is the stable aggregate job. It requires resolution, the fork artifact when applicable, and every required matrix lane. Cancellation, missing jobs and required-lane failures do not become successful qualification. GitHub checks and job summaries show the result; `qualification-*` artifacts contain per-lane provenance, failures, consumer CLI output and tested npm tarballs.

The scheduled `Pi release canary` checks all default branches against the latest stable release and the maintained fork, including the existing owned npm releases. It uses Actions concurrency and keeps exactly one native GitHub issue per affected repository, covering both official and fork hosts. Each run updates that issue with the latest lanes and closes it once every required lane for the repository passed with complete evidence; owner-waived Windows lanes are listed as diagnostics but do not keep an issue open. Older per-host/per-version issues for the same repository are folded into the single issue and closed. A failed runner without package evidence gets an infrastructure issue, closed by the next successful fleet run. The canary creates no repair PR, publishes nothing, and never updates a user's Pi installation.

Repairs use the repository's ordinary PR process. A fixture or host-selection failure is repaired there; a product failure gets a focused regression and source fix. The automation's own native tests deliberately introduce factory/startup failures and require the real bundled CLI to reject them, proving that the gate cannot pass solely because a process started. Metadata tests cover incomplete publication and exact cohort selection; resolver-entrypoint tests cover default and fork-only lanes, source refs and fail-closed selection with mocked external fetches; report tests cover one issue per repository across hosts, legacy-issue consolidation, owner-waived diagnostics and complete-evidence closure.

## Automatic npm releases

`fleet.json#npmRelease` enables the twelve existing owned npm channels plus five scoped channels, in release priority order: `@fitchmultz/pi-subagents`, `@fitchmultz/pi-calculator`, `@fitchmultz/pi-ask-question`, `@fitchmultz/pi-workflows`, `@fitchmultz/pi-verbosity-control`. Browser Native, Oracle and Cursor retain `approval`; all fourteen others use `automatic`. The five unscoped names belong to other projects and are **not** these packages; do not publish to or modify them. Existing twelve names, version lines and policies are unchanged. Archived and remaining Git-only packages are excluded. Standard public GitHub-hosted runners are used; release builds have no cache and candidate artifacts expire after seven days.

### Maintainer flow

1. Choose an intentional **stable `x.y.z` version**, update the lockfile normally, and add its nonempty versioned `CHANGELOG.md` section in a PR. Complete the package's applicable review/manual release requirements before merging; automation does not decide versions or replace those requirements.
2. Merge the PR to `main`. The package's `npm-release.yml` calls the pinned release plan, its existing offline CI workflows, and the shared publisher. Planning has push access solely because GitHub requires it to read unfinished drafts; it runs pinned automation, never package code, and performs no release writes. Package builds/checks stay read-only. A direct push is not a release authorization. Existing npm versions are never overwritten and unchanged versions do not ship new source changes.
3. The planner resolves latest official/fork identities once and forwards them through every required check and publication job. Preparation builds once against that selected official SDK without publishing credentials, restores locked bundled dependencies without rebuilding, then installs **the same tarball** into independent consumers of both resolved latest hosts and exercises their real bundled Pi CLIs. The run summary and `npm-candidate-COMMIT` artifact identify the exact hosts, package version, commit and checksum. The `npm-fork-host-COMMIT` artifact retains that preparation's exact fork archives and receipt for post-publication installed-consumer verification; both artifacts expire after seven days.
4. For the three approval packages, download that candidate and satisfy the existing exact-commit/tarball requirements before approving the **npm** environment. Browser's live-site/lifecycle evidence and reviewer requirements, Oracle's fresh all-preset proof/platform gates, and Cursor's release review/catalog and necessary focused evidence remain local prerequisites. Approval attests that real evidence was checked; it does not manufacture proof or waive a failed/unavailable gate. No browser/provider credentials or paid live campaigns move into CI.
5. Publication rechecks repository/npm identity, environment protection, source freshness, tag identity and archive checksums. It creates an annotated tag and draft GitHub Release, publishes the verified tarball using npm OIDC (or the bounded first-scoped-publication path below) with lifecycle hooks disabled, verifies exact registry integrity, then makes the GitHub Release public. npm provenance and per-run verification receipts identify the build.

A daily **12:17 UTC** run and manual dispatch reconcile missed publications. Already-published versions are read-only no-ops, except this automation's matching unfinished draft can be completed without republishing npm. After successful publication or exact-source recovery, verification waits up to seven minutes total for the exact version, package version entry and `latest` to propagate, within the unchanged ten-minute publish job. Only registry 404s or missing/stale visibility are retried; other HTTP, network, identity and integrity errors fail immediately. Requests retain their thirty-second limit, capped by the shared remaining visibility time. Rerun a failed job while its candidate artifact is retained; a changed archive, conflicting tag, unrecognized release or older version fails closed rather than overwriting user data. If `main` advanced before an unpublished candidate was approved, dispatch a new run on current `main`. A published immutable version can still have its original failed GitHub finalization retried. Never use a version bump just to hide an unknown publication outcome.

### One-time configuration and controls

- Each repository's **npm** environment permits only branch `main`; Browser Native, Oracle and Cursor require `fitchmultz` as reviewer. The publisher checks these protections again before release writes. Other environment settings and automated Cursor PR reviews are not changed.
- npm requires the package to exist before trusted publishing can be configured. For a genuine first release, use an intentional reviewed patch within the repository's existing version line, versioned notes and all normal latest official/fork checks. Only a registry **404** for the enabled exact `@fitchmultz/REPO` channel permits absence; all other statuses and existing-package ownership/source checks fail closed. Do not invent a previous version, reserve a dummy package or reset the version line.
- For the five new scoped channels only, place the already-validated package-write/bypass-2FA credential in each main-only **npm** environment as `NPM_BOOTSTRAP_TOKEN`. The reusable workflow declares that secret as optional, and each scoped caller's publish job explicitly maps `NPM_BOOTSTRAP_TOKEN: ${{ secrets.NPM_BOOTSTRAP_TOKEN }}` under `secrets`. The caller expression is empty when the credential is stored only in the environment; the called publish job's `npm` environment supplies the value. This declaration plus named mapping is the verified delivery shape; the undeclared, unmapped call received nothing in [the protected-main diagnostic](https://github.com/fitchmultz/pi-subagents/actions/runs/37322169888). Do not copy the credential into repository scope or use `secrets: inherit`. Preparation/tests never receive it. After artifact, caller, environment, current-main, release and tag checks, publication requires the credential and verifies `fitchmultz` before any GitHub release writes. Only the npm child receives it through `NODE_AUTH_TOKEN` and an owned 0600 registry-scoped placeholder config; it is never an argument or receipt. If metadata is now 200 (including a package appearing since planning), publication/recovery uses OIDC only, regardless of a leftover secret. Lifecycle hooks remain disabled; provenance and exact registry integrity/maintainer checks remain required.
- Direct bypass-token publishing currently has a January 2027 vendor ceiling; recheck npm's native first-publish path if bootstrap is still needed then. After each real pipeline first publication, configure and read back its native trust below, then remove only its temporary environment secret. Do not rotate/revoke the reused source credential or alter the twelve existing trust configurations.
- Configure each existing npm package to trust its own repository, caller filename **npm-release.yml**, and environment **npm**, with direct publishing allowed. Reusable workflows authenticate as their caller. This requires an npm account login/2FA, not a bypass-2FA `NPM_TOKEN`:

  ```sh
  npm trust github PACKAGE --repo fitchmultz/REPO --file npm-release.yml --env npm --allow-publish --yes
  ```

- For existing channels, verify workflows, approval environments and npm trust before enabling the repository variable. For the five first scoped publications, enable it after the reviewed source, green qualification, main-only environment and bootstrap credential are verified; publish first, then configure/read back native trust and remove the temporary secret:

  ```sh
  gh variable set NPM_RELEASE_ENABLED --repo fitchmultz/REPO --body true
  gh workflow run npm-release.yml --repo fitchmultz/REPO --ref main
  ```

- Set `NPM_RELEASE_ENABLED=false` to stop new release runs; also cancel any already-running or approval-pending run. Do not delete an existing npm version, move a conflicting tag or replace a release asset to recover an error.
- Prereleases and non-`latest` channels remain manual until a deliberate version/dist-tag policy is added. Existing manual publishing paths remain available. Distinguish registry-visible first **token-authenticated pipeline publication with provenance**, native **trust configured**, an already-published-version **no-op**, and the next genuine **OIDC publication**. Neither configured trust nor a no-op proves real OIDC publication; never manufacture a test bump to claim it.

The read-only plan and candidate verifier are runnable locally; `node scripts/npm-release.mjs --help` gives commands and exit codes. All package CI keeps its existing contracts through `workflow_call`, including Browser native lifecycle, Cursor native-platform/installed-form checks and MCP extras.

## Rollout and administration

1. Qualify the full candidate fleet on PR branches. `PI_COMPATIBILITY_SOURCE_REF` may temporarily select the coordinated rollout branch in this repository and the fork; clear it after the extension branches merge.
2. Obtain the required owner-designated reviews before merging or activating the rollout. Publish the shared workflow's version tag only after approval, then keep callers pinned to its reviewed commit.
3. Install the managed Renovate App for the selected repositories, using the owner's normal GitHub authentication. Do not run a second dependency updater.
4. Require each repository's actual successful aggregate compatibility check on its default branch, preserving existing protection and useful required checks. The fork includes reverse-dependency qualification in its existing `build-check-test` aggregate.
5. Set this repository's `PI_COMPATIBILITY_ENABLED` Actions variable to `true` to enable the canary, and run it once manually. Until then both its scheduled and manual entrypoints remain disabled.

A development-dependency-only change does not require a new npm release. For a shipped fix on an owned npm channel, publish the exact checked tarball and verify package/tag/source identity; retain any package-specific live release gates. Git-only packages stay Git-delivered. Consumer updates use normal Pi package updates and a fresh process or the fork's native restart. Qualification itself never activates code.

## Local checks

Node 24 runs the native Renovate validator. Pi host qualification and the unit/native tests also run on Node 22.22.2, the floor required by the pinned npm 12 release.

```sh
npm ci --ignore-scripts
npm rebuild re2
npm test
npm run check:renovate
actionlint
PI_TEST_HOST=/path/to/installed/pi-consumer npm run test:native

node scripts/qualify.mjs --repo pi-calculator --source /path/to/checkout \
  --host official --target latest --output /tmp/pi-qualification

node scripts/pack-fork.mjs /path/to/built/fork /tmp/fork-package FULL_FORK_SHA
node scripts/qualify.mjs --repo pi-calculator --source /path/to/checkout \
  --host fork --target /tmp/fork-package --output /tmp/pi-fork-qualification
```

A Pi consumer directory contains its own `node_modules/@earendil-works/pi-coding-agent` installation, not a manually linked dependency tree. Fork packing requires the native offline build first and a new output directory; it never rebuilds or replaces an existing output. Repository-local output is allowed only inside the fork's `.artifacts` directory. The native artifact manifest and hash-suffixed `tarballs/` archives are retained alongside `receipt.json`; receipt package files are relative to that directory and their SHA-256 values cover the physical archives. Local qualification copies uncommitted tracked/untracked source into a disposable checkout; CI checks immutable commits. Evidence records when a local source checkout was dirty.
